# アーキテクチャ方針

## 目的と今回の範囲

MCP クライアントが OAuth で接続できる入口を設け、ラッパーのサーバー側で Pleasanter 用 API キーを付けて既存 MCP サーバーへ中継します。MCP のツール・リソースは Pleasanter 側を利用し、ラッパーでは再実装しません。

今回整えたのは .NET 10 アプリ、起動確認、未実装応答、HTTP テスト、エージェント運用、Actions、参照ソース、AGPL ライセンスです。認証と中継はまだ実装していません。

## 実ソースで確認した事実

参照日 2026-10-06。根拠は `_reference/Implem.Pleasanter` の `Pleasanter_1.5.8.1` です。実機検証は未実施です。

- `Implem.Pleasanter/MCP/Infrastructure/McpConstants.cs`：MCP パスは `/mcp`。
- `Implem.Pleasanter/MCP/Infrastructure/McpApiKeyHelper.cs`：`X-API-Key` を優先し、無い場合は `Authorization: Bearer` から API キーを取得する。Bearer を受け付けること自体は OAuth トークン検証の実装を意味しない。
- `Implem.Pleasanter/Startup.cs`：`Parameters.McpServer.Enabled` に応じて HTTP トランスポートと `MapMcp` を登録する。
- `Implem.Pleasanter/MCP/Infrastructure/McpContextMiddleware.cs`：`Mcp-Session-Id` を扱う。
- `LICENSE`：GNU AGPL v3。

## 次の実装で扱うこと

1. 組織の IdP と認可サーバーの配置を決める。外部 IdP のトークン検証だけで必要なクライアント互換性を満たせるかを先に確認する。
2. MCP Authorization 仕様に沿って Protected Resource Metadata と認可サーバー discovery、401 challenge を提供する。Authorization Code + PKCE、クライアント登録方式、resource／audience を検証する。
3. トークンの署名・issuer・audience・有効期限・scope と組織所属を検証し、Pleasanter API キーへの対応を管理する。組織共有キーと利用者別キーのどちらを使うかは未決定。Pleasanter 側の権限と監査主体が変わるため、実装前に決める。
4. クライアントの Authorization と X-API-Key は上流へそのまま渡さず、サーバー管理の API キーを設定する。資格情報は設定ファイルやログ、クライアントへ出さない。
5. Streamable HTTP の GET／POST／DELETE、SSE の逐次転送、キャンセル、セッション ID、プロトコルヘッダーを保つ中継を実装する。セッションは認証主体との対応も確認する。
6. Claude など対象クライアントと Pleasanter 実機でコネクタ接続を検証する。

公開 URL は HTTPS を前提とします。認可サーバーの実装方式やデプロイ先は今回決め打ちしていません。
