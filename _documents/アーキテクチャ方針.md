# アーキテクチャ方針

## 認証と中継

OpenIddict による Authorization Code + PKCE（S256）の認可サーバーと、YARP による HTTP 中継を提供する。MCP のツール・メッセージは解釈せず、GET／POST／DELETE と SSE を Pleasanter に中継する。Pleasanter のアセンブリ・MCP ツール定義・バージョン番号には依存しない。

ログイン時は固定 TenantId 内の LoginId に対応する Users をパラメーター化した SELECT で取得し、SHA-512 のパスワードハッシュを固定時間比較する。本体の無効化・ロックアウト・パスワード変更要求・期限を確認する。DB への書き込みは行わない。本体のパスワード方式と Users の列構造は互換性の前提となるため、あらゆる将来バージョンに無条件で対応する保証ではない。

利用者は個人または管理者が指定した共通アカウントを選び、認可画面で確認する。OAuth の主体はログインした本人で、API キー所有者 ID を別に保持する。共通キーの場合、Pleasanter 側の操作主体・権限・監査は共通アカウントになる。

API キーは MCP 通信ごとに Users から取得し、その通信中だけメモリ上で使用する。ラッパーの DB、ファイル、トークン、セッションへキーを保存・キャッシュしない。受信 Authorization、X-API-Key、Cookie、転送元ヘッダーを除去し、上流へ X-API-Key を設定する。

## OAuth と状態

discovery、Protected Resource Metadata、401 challenge、認可・トークン・失効エンドポイントを提供する。許可した redirect URI の完全一致、PKCE、resource／audience、scope、クライアントとの対応、認可コードの一度だけの使用、トークンの失効を検証する。動的クライアント登録は明示的に有効化し、管理者の redirect URI 許可一覧に限定する。

ログイン・同意の POST は CSRF トークンを検証する。ログインの失敗回数はアカウントごとに永続化し、IP ごとのレート制限も行う。同意チケットには認可リクエストを結び付け、有効期限と一度だけの使用を検証する。パスワードを OAuth エンドポイントへ送らない。

独自 SQLite DB に保存するのは OAuth クライアント、認可・トークンの状態、短命の同意 nonce、ログイン試行制限である。トークン内部には利用者・キー所有者 ID とパスワード変更検知用スタンプを格納する。API キーとパスワードは格納しない。アクセストークンは 15 分、認可コードは 2 分、リフレッシュトークンは 1 日。有効性の判定にトークン DB と Users の最新状態を使う。

MCP セッション ID は利用者・キー所有者・OAuth クライアントに結び付けて暗号化する。別主体のセッション利用を拒否する。開始済みの長時間通信中に DB を再照会することはなく、変更を反映するのは次の HTTP リクエストである。

## DB の互換性と制約

参照した本体は `Pleasanter_1.5.8.1`（2026-10-06）。SELECT 対象列は TenantId、UserId、LoginId、Password、ApiKey、Disabled、Lockout、PasswordExpirationTime、LoginExpirationLimit、LoginExpirationPeriod、LastLoginTime、EnableSecretKey。本体の Rds.json と同じ `App_Data/Parameters/Rds.json` のフラットな配置を使い、接続には読み取り専用の UserConnectionString だけを使う。Sa／Owner 接続文字列は使わない。

PostgreSQL、SQLServer、MySQL の ADO.NET ドライバーと識別子の引用に対応する。自動テストは SQLite の Users フィクスチャで認証・中継の流れを確認しており、これら 3 DB の実機互換性確認を代替しない。

この初期版は単一インスタンス運用で、SQLite と Data Protection の状態領域を永続化する。本体の最終ログイン・失敗回数・監査ログは更新しない。二段階認証・パスキー・外部認証は再実装せず、設定上有効なら起動を拒否する。本体の IP 制限など入口側のポリシーは配置側で適用する。

## 検証

24 件の HTTP テストで OAuth、同意、PKCE、コード再利用、CSRF、SQL 注入、失効・更新、キー変更・削除、利用者の無効化・期限、共通アカウント、主体をまたぐセッション、Origin、URL 内トークンの拒否、SSE の逐次転送を確認した。Pleasanter 本体・実 DB・Claude 組織コネクタ・本番証明書を通した検証は未実施。
