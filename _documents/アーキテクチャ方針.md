# アーキテクチャ方針

## 認証と中継

OpenIddict による Authorization Code + PKCE（S256）の認可サーバーと、YARP による HTTP 中継を提供する。MCP のツール・メッセージは解釈せず、GET／POST／DELETE と SSE を Pleasanter に中継する。Pleasanter のアセンブリ・MCP ツール定義・バージョン番号には依存しない。

ログイン画面では API キーだけを入力し、固定 TenantId 内の Users と照合して利用者を特定する。SQL はパラメーター化し、キーの照合が大文字小文字を区別しないデータベースでも、取得した値と固定時間比較する。重複キーは拒否する。無効化・ロックアウト・利用期限を確認し、データベースへの書き込みは行わない。Password と TOTP 登録状態は認証に使わない。

個人の API キーで認証した利用者は、個人または管理者が指定した共通アカウントを選び、認可画面で確認する。OAuth の主体はログインした本人で、API キー所有者 ID を別に保持する。共通キーの場合、Pleasanter 側の操作主体・権限・監査は共通アカウントになる。

共通の API キーで直接ログインした場合は、共通アカウントを主体とし、利用者個人は識別できない。

API キーは MCP 通信ごとに Users から取得し、その通信中だけメモリ上で使用する。ラッパーのデータベース、ファイル、トークン、セッションへキーを保存・キャッシュしない。受信 Authorization、X-API-Key、Cookie、転送元ヘッダーを除去し、上流へ X-API-Key を設定する。

## OAuth と状態

discovery、Protected Resource Metadata、401 challenge、認可・トークン・失効エンドポイントを提供する。許可した redirect URI の完全一致、PKCE、resource／audience、scope、クライアントとの対応、認可コードの一度だけの使用、トークンの失効を検証する。動的クライアント登録は明示的に有効化し、管理者の redirect URI 許可一覧に限定する。

ログイン・同意の POST は CSRF トークンを検証する。ログインの失敗回数は接続元 IP ごとに永続化し、IP ごとのレート制限も行う。同意チケットには認可リクエストを結び付け、有効期限と一度だけの使用を検証する。パスワードを OAuth エンドポイントへ送らない。

ログイン試行制限は接続元 IP ごとに15分で5回までとし、成功した試行の1回分だけを戻す（失敗の履歴は消さない）。同じ名前・redirect URI の動的登録は同じクライアントを返し、総数を MaxDynamicClients で制限する。

StateStore=Sqlite では独自 SQLite データベース、StateStore=Redis では Redis／Valkey 互換 KVS に保存する。保存対象は OAuth クライアント、認可・トークンの状態、短命の同意 nonce、ログイン試行制限である。トークン内部には利用者・キー所有者 ID と認証した API キーと接続用 API キーの再発行検知用 SHA-256 指紋を格納する。API キーの値とパスワードは格納しない。認証したキーまたは共通の接続用キーを削除・再発行すると、同意チケット・認可コード・アクセス／更新トークンを次の利用時に拒否する。アクセストークンは 15 分、認可コードは 2 分、リフレッシュトークンは 1 日。有効性の判定にトークンデータベースと Users の最新状態を使う。

MCP セッション ID は利用者・キー所有者・OAuth クライアントに結び付けて暗号化する。別主体のセッション利用を拒否する。開始済みの長時間通信中にデータベースを再照会することはなく、変更を反映するのは次の HTTP リクエストである。

## データベースの互換性と制約

参照した本体は `Pleasanter_1.5.8.1`（2026-10-06）。SELECT 対象列は TenantId、UserId、LoginId、ApiKey、Disabled、Lockout、LoginExpirationLimit、LoginExpirationPeriod、LastLoginTime。本体の Rds.json と同じ `App_Data/Parameters/Rds.json` のフラットな配置を使い、接続には読み取り専用の UserConnectionString だけを使う。Sa／Owner 接続文字列は使わない。

PostgreSQL、SQLServer、MySQL の ADO.NET ドライバーと識別子の引用に対応する。自動テストは SQLite の Users フィクスチャで認証・中継の流れを確認しており、これら 3種類のデータベースの実機互換性確認を代替しない。

SQLite モードは単一インスタンス運用で、SQLite と Data Protection の状態領域を永続化する。Redis モードは OpenIddict の独自 KVS ストアを使用し、クライアント登録・認可・トークン・同意・試行制限・Data Protection の鍵を共有する。共有するインスタンスでは Issuer、テナントと全設定、KvsKeyPrefix、署名・暗号化証明書を揃える。本体の最終ログイン・失敗回数・監査ログは更新しない。API キーの所有を認証根拠とし、二段階認証・パスキー・外部認証のログイン完了とは扱わない。Authentication.json と Security.json は使用しない。本体の IP 制限など入口側のポリシーは配置側で適用する。

## OAuth 用証明書

OAuth 証明書は、未指定時に有効期限10年で用途別に自動生成して永続化する。ファイル／Base64、Windows 証明書ストア、Azure Key Vault／AWS Secrets Manager／GCP Secret Manager／OCI Vault Secrets からの PFX 取得にも対応する。各用途の入力は排他で、取得失敗時に生成へ切り替えない。クラウド PFX は起動時にメモリ上へ読み込み、取得元の値をディスクに保存しない。Redis の複数台構成では自動生成領域も共有するか、同じ証明書を明示指定する。複数世代の同時登録によるローテーションとクラウドの非エクスポート鍵への処理委譲は未対応。設定は [OAuth 証明書の設定](OAuth証明書の設定.md) を参照。

## 検証

2026-10-10 の証明書方式追加時に Windows の Release ビルド（警告・エラー0件）と通常テスト96件の成功、KVS専用5件のスキップを確認した。Redis／Valkey では各101件すべて成功した。自動生成証明書での再起動後の状態復号、同時生成、暗号化証明書削除後の再生成で旧状態の復号が失敗すること、Windows ストアの非エクスポート鍵、クラウド取得後の PFX 読み込みと秘密を含めないエラー処理を確認した。クラウド実環境の認証・IAM・ネットワークを通す試験は未実施。

通常モードの自動テスト64件で OAuth、同意、PKCE、コード再利用、CSRF、SQL 注入、失効・更新、キー変更・削除、利用者の無効化・期限、共通アカウント、主体をまたぐセッション、Origin、URL 内トークンの拒否、SSE の逐次転送を確認した。Docker 上の Pleasanter 1.5.8.1／PostgreSQL 17 で個人・共通権限による OAuth、MCP 初期化・20ツールの取得、標準画面でのキー再発行後の旧トークン拒否を確認した。SQL Server 2025・PostgreSQL 17・MySQL 8.4 は Docker の検証用 Users を用いて接続・9列の SELECT・列変換・読み取り専用権限を確認した。SQL Server・MySQL に接続した Pleasanter 経由の OAuth/MCP、Claude 組織コネクタ・本番証明書を通した検証は未実施。

KVS モードでは69件を実行し、別インスタンス・再起動後の利用、同意・認可コードの原子的な消費、失効共有・古い版の更新拒否、API キー非保存を確認した。KVS ではクライアント ID と参照トークン ID の索引を持ち、同意と試行回数は TTL、OAuth 状態の更新はバージョン比較付き Lua を使う。使用済み認可コードと失効済み状態の復活は原子的に拒否する。
