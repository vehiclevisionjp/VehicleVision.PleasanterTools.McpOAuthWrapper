# 管理者向け導入手順

本書は初期版の設定手順です。Docker 上の Pleasanter 1.5.8.1／PostgreSQL 17 で OAuth と MCP 接続を確認しています。SQL Server 2025・PostgreSQL 17・MySQL 8.4 の読み取り専用接続と Users の SELECT も Docker で確認済みです。導入後は本書の接続確認を行ってください。

## 1. インストール

Windows または Linux に [ASP.NET Core Runtime 10](https://dotnet.microsoft.com/en-us/download/dotnet/10.0) をインストールします。.NET Runtime だけではなく、ASP.NET Core Runtime が必要です。ソースを変更しない利用者は SDK をインストールする必要はありません。

[Release ページ](https://github.com/vehiclevisionjp/VehicleVision.PleasanterTools.McpOAuthWrapper/releases)から使用するバージョンを選び、リリース説明を確認して Assets の **McpOAuthWrapper.zip** をダウンロードします。Source code (zip)／Source code (tar.gz) はソースコード用で、インストール用の配布物とは異なります。ダウンロードした ZIP を展開してください。

Windows では、例えば `C:\Apps\McpOAuthWrapper` に展開します。Linux では、アプリ実行アカウントが使う配置ディレクトリーに `unzip` で展開します。展開先直下に `VehicleVision.PleasanterTools.McpOAuthWrapper.dll`、`appsettings.json`、`App_Data/Parameters` があることを確認します。`BUILD.txt` には配布物の元となったソースのコミットを記載しています。

まず展開先をカレントディレクトリーにして、接続を無効にした初期設定のまま起動確認します。

```text
dotnet --list-runtimes
dotnet VehicleVision.PleasanterTools.McpOAuthWrapper.dll --urls http://127.0.0.1:5180
```

`http://127.0.0.1:5180/health/live` にアクセスして `Healthy` が表示されれば、アプリの配置とランタイムを確認できています。`/mcp` は接続未設定の 501 を返します。Ctrl+C で停止し、以下の設定を行います。

## 2. Pleasanter とデータベース

Pleasanter の MCP サーバーを有効にし、利用者または共通アカウントの API キーを Pleasanter で発行します。キーはラッパーの接続画面に入力して認証に使います。設定ファイルには登録せず、ラッパーにも保存しません。

ラッパーの配置先に `App_Data/Parameters/Rds.json` を用意します。付属の Rds.example.json は本体と同じフラットなレイアウトです。Dbms は PostgreSQL／SQLServer／MySQL、Provider は Local。UserConnectionString に Users の必要列だけを SELECT できる専用の読み取り専用接続を設定します。SaConnectionString と OwnerConnectionString は使用せず空にしてください。接続文字列の `#ServiceName#` などのプレースホルダーは展開しません。

Windows で設定例を配置する場合は、展開先で次を実行し、作成した2ファイルを構成に合わせて編集します。General.json はラッパー専用の設定、Rds.json は Pleasanter のデータベースへの接続設定です。既存の設定がある場合はコピーせず、内容を確認してください。Linux では同じファイルを `cp` で配置できます。

```powershell
Copy-Item App_Data/Parameters/General.example.json App_Data/Parameters/General.json
Copy-Item App_Data/Parameters/Rds.example.json App_Data/Parameters/Rds.json
```

UserConnectionString は環境変数 `MCP_RDS_UserConnectionString` でも上書きできます。SqlCommandTimeOut は 1～120 秒に設定します。本体用の管理者接続をそのまま持ち込まないでください。

API キーで認証するため Authentication.json／Security.json は使用しません。Pleasanter のパスワードや LDAP・パスキー・二段階認証の設定を変更する必要はありません。API キーを使う接続を組織の運用方針として許可していることを確認してください。

## 3. ラッパーの設定

ラッパーの設定は `App_Data/Parameters/General.json` にフラットな形式で指定します。`appsettings.json` を編集する必要はありません。ファイルと環境変数のどちらにも設定がない場合は接続を無効にして起動します。

配置ごとの上書きには `MCP_GENERAL_項目名` の環境変数を使用できます。例えば証明書パスワードは `MCP_GENERAL_CertificatePassword`、クライアントの項目は `MCP_GENERAL_Clients__0__ClientId` です。環境変数がファイルの設定より優先されます。General.json は Pleasanter からコピーせず、ラッパーに付属する General.example.json を使ってください。

旧設定の `ApiKeyLoginId` は使用しません。既存の General.json や環境変数から削除してください。

設定例では、利用者や接続元 IP の追加許可リストを設けません。OAuth の PKCE・接続先検証、アカウント状態の検証、ログイン試行制限と MCP の Origin 検証は認証を保護するために適用します。設定が済むまでは Enabled=false とします。

例えば PleasanterUrl に `https://pleasanter.example/portal` を指定すると、`https://pleasanter.example/portal/` として扱い、MCP の接続先は `https://pleasanter.example/portal/mcp` になります。OAuth クライアントの redirect URI は補完せず、登録した値との完全一致で検証します。

| 項目 | 設定内容 |
| --- | --- |
| Enabled | 設定完了後に true。初期値 false では `/mcp` は 501 |
| Issuer | ラッパー専用ホストのルート HTTPS URL。末尾 `/` は省略可、自動補完 |
| PleasanterUrl | 上流 Pleasanter のベース HTTPS URL。サブパス可、末尾 `/` は省略可、自動補完 |
| TenantId | 接続を許可するテナント ID |
| DatabaseTimeZoneId | 本体がデータベースに日時を保存する際のタイムゾーン。初期値 UTC。日本時間なら Asia/Tokyo |
| SharedApiKeyUserId | 認証したアカウントに加えて選択できる共通アカウントの数値 UserId。同じテナント内に限定。null でこの追加選択肢を表示しない |
| StateStore | Sqlite（既定）または Redis。Redis は Valkey 互換 KVS にも接続可能 |
| KvsConnectionString | Redis モードの接続文字列。環境変数 MCP_GENERAL_KvsConnectionString から供給 |
| KvsKeyPrefix | KVS 内の専用名前空間。既定 pleasanter-mcp-oauth。同じラッパーのインスタンス間だけで共有 |
| StateDirectory | SQLite モードの OAuth 状態・Data Protection 鍵と、自動生成証明書の永続ディレクトリー。初期値 App_Data/Wrapper。Redis モードでも証明書の自動生成に使用 |
| SigningCertificatePath / EncryptionCertificatePath | ファイル方式の秘密鍵付き PFX のパス。他の方式を使う用途は空にする |
| SigningCertificateBase64 / EncryptionCertificateBase64 | Base64 方式の秘密鍵付き PFX。環境変数 MCP_GENERAL_SigningCertificateBase64／MCP_GENERAL_EncryptionCertificateBase64 から供給 |
| SigningCertificateThumbprint / EncryptionCertificateThumbprint | Windows 証明書ストアの証明書の拇印。他の方式を使う用途は空にする |
| CertificateStoreName / CertificateStoreLocation | Windows ストアの名前と場所。既定 My／CurrentUser。IIS などのマシンストアは My／LocalMachine |
| SigningCertificateCloud / EncryptionCertificateCloud | クラウド方式。Provider（Azure／AWS／GCP／OCI）、SecretId、必要に応じて Version／Region／OCI 認証方式を設定。詳しくは [OAuth 証明書の設定](OAuth証明書の設定.md) |
| CertificatePassword | 2枚の PFX に共通のパスワード。Key Vault の証明書から取得する PFX では空。General.json へ平文で書かず、環境変数 MCP_GENERAL_CertificatePassword や配置環境の秘密管理から設定 |
| TrustedProxyAddresses | HTTPS 終端プロキシを使う場合、その送信元 IP の明示的な一覧。1 段の転送ヘッダーを信頼。**プロキシ配下で未設定だと、全利用者が同じ接続元に見え、ログイン試行制限（接続元ごとに15分で5回）を共有します。** 転送ヘッダーが処理されずに届くと警告をログへ出します |
| AllowedOrigins | MCP リクエストの許可 Origin の追加一覧。完全一致。既定で同一 Origin と Origin なしを許可 |
| MaxDynamicClients | 動的登録で作成できるクライアント数の上限。初期値 100、1～10000。同じ名前と redirect URI の登録は同じ client_id を返し、上限を超えると 503 |

OAuth の状態領域と証明書をアプリ実行アカウントだけが読み書きできるようにします。SQLite モードは単一インスタンスで運用してください。ログイン試行制限の排他もプロセス内だけなので、複数インスタンスでは制限がインスタンスごとになります。複数台構成には Redis モードを使用します。Redis モードでは、同じ KVS・名前空間・証明書を使うインスタンス間で OAuth の状態を共有できます。状態領域を消すと発行済みの認可・トークン・セッションを利用できなくなります。

プロキシを使う場合は、Issuer のホストと HTTPS を伝えるヘッダーを設定し、TrustedProxyAddresses を指定します。公開 URL と実際の Host／scheme の不一致は拒否します。appsettings.json の `AllowedHosts` は既定の `*` のままで構いません。ヘルスチェック以外は、アプリ自身が Host と scheme を Issuer と照合して拒否します。入口で本体と同等のネットワーク制限を適用してください。

例えば、同じマシンの HTTPS 終端プロキシから `127.0.0.1:5180` へ転送する場合は、Issuer に公開 URL、TrustedProxyAddresses に `127.0.0.1` を指定します。プロキシは公開ホストの `X-Forwarded-Host` と `X-Forwarded-Proto: https` を送信してください。外部からアプリの HTTP ポートへ直接接続できない配置にします。

OAuth 証明書の方式は用途ごとに一つ選びます。未指定の用途は初回起動時に有効期限10年の自己署名 RSA 4096 ビット証明書を自動生成し、StateDirectory/certificates に保存します。ファイル、Base64、Windows 証明書ストア、4クラウドからの PFX 取得も利用できます。これらは OAuth と状態保護に使う証明書で、公開 HTTPS 用証明書は終端プロキシ側で設定します。CertificatePassword とデータベース接続文字列を秘密管理から供給し、配置ファイル・状態領域をアプリ実行アカウントだけが利用できるようにしてください。方式ごとの設定と更新上の注意は [OAuth 証明書の設定](OAuth証明書の設定.md) を参照してください。

アプリ実行環境は Production とします。Windows の起動確認では `$env:ASPNETCORE_ENVIRONMENT = 'Production'`、Linux では `export ASPNETCORE_ENVIRONMENT=Production` を設定してから起動します。Development でも同じ証明書の読み込み方式を使いますが、HTTP 許可は開発環境専用です。

### OAuth 用証明書を生成する

未指定の場合は自動生成されるため、手動生成は不要です。自分で生成した PFX を指定する場合は、以下のファイル方式の生成手順を使います。秘密鍵の欠落、有効期間外、保存済み PFX の破損やパスワード不一致では起動できません。明示指定した方式の失敗時に自動生成へ切り替わることはありません。両方の PFX を同じパスワードで出力し、その値を CertificatePassword に設定します。Azure で証明書を Key Vault から読み込む場合は、配置先の Key Vault 手順または [クラウドからの直接取得](OAuth証明書の設定.md#クラウドからの直接取得) を使用してください。

[OpenIddict の公式資料](https://documentation.openiddict.com/configuration/encryption-and-signing-credentials.html)に沿って、HTTPS 用とは別の RSA 4096 ビットの自己署名証明書を2枚生成します。OAuth 用証明書のため、HTTPS のドメイン証明書の購入やクライアントへのルート証明書のインストールは不要です。

生成作業には Windows／Linux の PowerShell 7（pwsh）を使います。アプリ実行環境に PowerShell 7 を追加する必要はなく、管理用端末で生成して配置できます。次のコードを PowerShell 7 で実行します。カレントディレクトリーの oauth-certificates に PFX を作り、有効期間を2年間に設定します。パスワードは画面に表示せず入力します。

```powershell
$ErrorActionPreference = 'Stop'
$certificateDirectory = Join-Path $PWD 'oauth-certificates'
foreach ($name in @('signing', 'encryption')) {
    if (Test-Path (Join-Path $certificateDirectory "$name.pfx")) {
        throw "$name.pfx が既にあります。既存の証明書を上書きしないでください。"
    }
}
New-Item -ItemType Directory -Path $certificateDirectory -Force | Out-Null
$securePassword = Read-Host '2枚の PFX に共通のパスワード' -AsSecureString
$password = [System.Net.NetworkCredential]::new('', $securePassword).Password
if ([string]::IsNullOrWhiteSpace($password)) { throw 'パスワードを入力してください。' }

foreach ($name in @('signing', 'encryption')) {
    $rsa = [System.Security.Cryptography.RSA]::Create(4096)
    $request = [System.Security.Cryptography.X509Certificates.CertificateRequest]::new(
        "CN=McpOAuthWrapper $name", $rsa,
        [System.Security.Cryptography.HashAlgorithmName]::SHA256,
        [System.Security.Cryptography.RSASignaturePadding]::Pkcs1)
    $usage = if ($name -eq 'signing') {
        [System.Security.Cryptography.X509Certificates.X509KeyUsageFlags]::DigitalSignature
    } else {
        [System.Security.Cryptography.X509Certificates.X509KeyUsageFlags]::KeyEncipherment
    }
    $request.CertificateExtensions.Add(
        [System.Security.Cryptography.X509Certificates.X509KeyUsageExtension]::new($usage, $true))
    $now = [DateTimeOffset]::UtcNow
    $certificate = $request.CreateSelfSigned($now.AddMinutes(-5), $now.AddYears(2))
    try {
        $pfx = $certificate.Export(
            [System.Security.Cryptography.X509Certificates.X509ContentType]::Pfx, $password)
        [System.IO.File]::WriteAllBytes((Join-Path $certificateDirectory "$name.pfx"), $pfx)
    } finally {
        $certificate.Dispose()
        $rsa.Dispose()
    }
}
Remove-Variable password, pfx
$securePassword.Dispose()
```

生成した signing.pfx と encryption.pfx を、配布物の更新で上書きされない保護されたディレクトリーへ配置し、アプリ実行アカウントに読み取り権限を付けます。Linux では専用アカウントを所有者にして、ディレクトリーは 700、PFX は 600 などに制限します。PFX とパスワードを Git や公開 ZIP に含めないでください。

General.json の該当項目を、配置先に合わせて次のように設定します。以下は Windows の例です。Linux では /var/lib/mcp-oauth-wrapper/certs/signing.pfx などの絶対パスに置き換えます。

```json
{
  "SigningCertificatePath": "C:\\ProgramData\\McpOAuthWrapper\\Certs\\signing.pfx",
  "EncryptionCertificatePath": "C:\\ProgramData\\McpOAuthWrapper\\Certs\\encryption.pfx"
}
```

相対パスはアプリのコンテンツルートを基準に解決されるため、配置時は絶対パスを指定します。CertificatePassword は上で入力した共通パスワードを環境変数 MCP_GENERAL_CertificatePassword として実行プロセスへ渡します。Azure App Service では「環境変数」のアプリ設定にこの名前で登録し、保存して再起動します。IIS や OS サービスでもアプリの実行プロセスに渡してください。生成用端末で環境変数を設定しただけでは配置先には反映されません。

PFX の有効期限を管理し、期限前に更新します。暗号化用証明書は Data Protection の鍵の保護にも使用するため、更新時は既存の状態領域と旧証明書をバックアップしてください。

## 4. AI アプリの登録

事前登録する場合は Clients に ClientId、DisplayName、RedirectUris を指定します。クライアントの redirect URI を実際の設定から確認し、完全一致で登録します。ワイルドカードは使えません。公開クライアントとして Authorization Code + PKCE S256 を使用します。

動的登録を要求するクライアントでは AllowDynamicClientRegistration を true とし、AllowedRedirectUris に同じ完全一致の許可一覧を設定します。登録エンドポイントは `/connect/register` です。動的登録を有効にするだけでは任意の転送先を受け入れません。登録は認証なしで受け付けるため、同じ名前と redirect URI の再登録は既存のクライアントを返し、総数は MaxDynamicClients で制限します。

AI アプリのコネクタ URL は `Issuer + mcp` です。未認証時の 401 から認可情報を取得し、ラッパーのログイン画面へ移ります。利用者の手順は [README](../README.md) を参照してください。

初期版では、Clients から設定を除いた場合も OAuth データベースの既存登録は自動削除しません。クライアントを廃止する際は停止中に、SQLite モードでは状態領域、Redis モードでは専用名前空間の OAuth 状態と鍵を再作成して全認可を無効化し、残すクライアントを再登録します。全利用者が再接続する必要があります。

## 5. 起動と確認

設定が完了したら General.json の Enabled を true にし、展開先から再起動します。HTTP 終端プロキシを使う場合の起動コマンドは、最初の起動確認と同じです。

```text
dotnet VehicleVision.PleasanterTools.McpOAuthWrapper.dll --urls http://127.0.0.1:5180
```

常時運用では、このコマンドを配置環境のサービス管理へ登録してください。カレントディレクトリーを展開先に設定し、実行アカウント・秘密の環境変数・状態領域の永続化を指定します。

`/health/live` は起動確認、`/.well-known/oauth-protected-resource` と `/.well-known/oauth-authorization-server` は discovery 用です。個人／共通アカウントで接続し、Pleasanter 側の権限と監査主体、API キー再発行・削除、利用者無効化を確認してください。

API キー未発行のアカウントは最初のログイン認証を通りません。先に Pleasanter で発行してから接続してください。入力したキーから利用者を検索するため、未発行と入力間違いを区別して表示しません。個人キーの認証後に共通アカウントを選び、その共通キーが未発行の場合は発行案内を表示します。キーやアカウントを無効にした場合、次の MCP 通信は拒否されます。既に開始している長時間通信をその場で停止する機能はありません。

## 6. 更新と困ったとき

パスワード認証版から更新した場合は、既存の OAuth 認可を引き継がず、発行済みの API キーで再接続してください。古いトークンは新しい認証方式では拒否します。Authentication.json／Security.json はラッパーで使用しなくなりました。Pleasanter 側のファイルは変更しないでください。

旧版で appsettings.json の Bridge セクションを設定していた場合は、その中の項目を General.json の最上位へ移してください。旧版の `Bridge__項目名` 環境変数は `MCP_GENERAL_項目名` に変更します。

更新時はアプリを停止し、新しい配布 ZIP を別のディレクトリーへ展開します。既存の Rds.json、General.json、証明書、StateDirectory の内容を引き継ぎ、起動確認後に転送先を切り替えます。初期版では OAuth データベースの構造変更を自動移行する仕組みはありません。配布元の変更内容を確認し、データベース構造変更がある更新では再認可が必要になる場合があります。

| 状況 | 確認すること |
| --- | --- |
| 起動時にランタイム不足が表示される | ASP.NET Core Runtime 10 をインストールしたか |
| `/mcp` が 501 | General.json の Enabled が false のままか |
| 接続が 400 | Issuer と公開ホスト・HTTPS・転送ヘッダーが一致しているか |
| ログインできない | 入力した API キー、キー所有者の状態、TenantId。失敗が続いた場合は15分待つ |
| 共通アカウントの API キーが利用できないと表示される | 管理者が指定した共通アカウントのキー発行、アカウント状態、TenantId |
| データベース接続エラー | Dbms、読み取り専用接続、Users の SELECT 権限、ネットワーク経路 |
| AI アプリが接続できない | 登録した redirect URI の完全一致、PKCE S256、公開 URL と証明書 |

## 7. Azure App Service（Windows）

.NET 10 の Windows App Service に配置できます。[Microsoft の導入資料](https://learn.microsoft.com/en-us/azure/app-service/quickstart-dotnetcore)も参照してください。

1. Windows／.NET 10 の Web アプリを用意し、HTTPS のみを有効にします。対応するプランでは Always On を有効にします。SQLite モードではインスタンス数を1に固定します。KVS モードで状態を共有する構成は後述の手順を参照してください。
2. データベースへの経路を確保します。プライベートな接続先には VNet 統合などを設定し、Users の必要列だけを読める接続を用意します。
3. 配布物を展開し、General.example.json／Rds.example.json をコピーして前述の設定を行います。Issuer は App Service の公開 HTTPS URL です。秘密は App Service のアプリ設定で `MCP_RDS_UserConnectionString`、`MCP_GENERAL_CertificatePassword` として指定します。
4. 証明書は後述の Key Vault 方式、または前述の生成・ファイル配置方式を使用します。ファイル方式では2枚の PFX を用意します。Kudu で `%HOME%` を確認し、その配下の `data/McpOAuthWrapper` に状態領域と証明書を配置します。General.json の StateDirectory と証明書パスには、その環境の絶対パスを指定します。更新で上書きされる `wwwroot` に状態領域を置かないでください。
5. アプリのファイルを直下に含む ZIP を作り、[ZIP デプロイ](https://learn.microsoft.com/en-us/azure/app-service/deploy-zip)で配置します。DLL と web.config が ZIP 直下に必要です。配置用の General.json はこの私用 ZIP に含めますが、秘密入りの ZIP を公開しないでください。

```text
az webapp deploy --resource-group <リソースグループ> --name <アプリ名> --src-path <配置ZIP> --type zip
```

アプリ設定に `ASPNETCORE_ENVIRONMENT=Production` を指定します。IIS 統合の転送設定は既定のまま利用し、TrustedProxyAddresses は空にします。追加のリバースプロキシを設ける場合だけ、その構成に合わせて明示します。再起動後、公開 URL の `/health/live` と discovery、認可から MCP 接続までを確認します。

### Azure Key Vault から証明書を読み込む

Key Vault 対応を含む配布物を使用してください。v0.2.0 の配布物は証明書の Base64 入力に対応していません。

App Service の [Key Vault 参照](https://learn.microsoft.com/en-us/azure/app-service/app-service-key-vault-references)で、証明書のシークレットをアプリ設定へ渡します。ラッパーは Base64 の PFX をメモリ上で読み込むため、証明書ファイルの手動配置は不要です。SQLite モードの状態領域は引き続き永続化します。

#### 1. Key Vault に2枚の証明書を用意する

署名用 mcp-oauth-signing と暗号化用 mcp-oauth-encryption を用意します。次は Azure CLI が利用できる管理用端末の PowerShell 7 で、自己署名・RSA 4096・有効期間2年・エクスポート可能な秘密鍵・PFX 形式の2枚を生成する例です。作成するアカウントには Key Vault Certificates Officer などの作成権限が必要です。

```powershell
$vaultName = '<Key Vault 名>'
foreach ($purpose in @('signing', 'encryption')) {
    $usage = if ($purpose -eq 'signing') { 'digitalSignature' } else { 'keyEncipherment' }
    $policy = @{
        issuerParameters = @{ name = 'Self' }
        keyProperties = @{ keyType = 'RSA'; keySize = 4096; exportable = $true; reuseKey = $false }
        secretProperties = @{ contentType = 'application/x-pkcs12' }
        x509CertificateProperties = @{
            subject = "CN=McpOAuthWrapper $purpose"
            keyUsage = @($usage)
            validityInMonths = 24
        }
    }
    $policyFile = Join-Path $PWD "mcp-oauth-$purpose-policy.json"
    $policy | ConvertTo-Json -Depth 5 | Set-Content -LiteralPath $policyFile -Encoding utf8NoBOM
    az keyvault certificate create --vault-name $vaultName --name "mcp-oauth-$purpose" --policy "@$policyFile" --output none
    if ($LASTEXITCODE -ne 0) { throw "$purpose 証明書の作成に失敗しました。" }
}
```

Key Vault の「証明書」の現在のバージョンに表示される「シークレット識別子」を控えます。参照先は /certificates/ ではなく /secrets/ の URL です。証明書と同名のシークレットから秘密鍵付き PFX を取得するため、エクスポート不可の鍵や RSA-HSM は使用できません。[証明書の構成とエクスポート条件](https://learn.microsoft.com/en-us/azure/key-vault/certificates/how-to-export-certificate)も参照してください。

#### 2. App Service に読み取り権限を付ける

App Service の「ID」でシステム割り当てマネージド ID を有効にします。Key Vault の「アクセス制御（IAM）」で、その ID に Key Vault Secrets User を割り当てます。アクセスポリシー方式の場合は、シークレットの Get 権限を付けます。証明書の公開部分だけを取得する権限では足りません。

Key Vault のネットワークを制限している場合は、App Service の VNet 統合と Private Endpoint などで到達できる経路も用意します。

#### 3. App Service のアプリ設定を登録する

App Service の「設定 → 環境変数 → アプリ設定」に、次の値を登録します。シークレット識別子は実際のバージョン付き URL に置き換えます。

| 名前 | 値 |
| --- | --- |
| MCP_GENERAL_SigningCertificateBase64 | `@Microsoft.KeyVault(SecretUri=https://<vault>.vault.azure.net/secrets/mcp-oauth-signing/<version>)` |
| MCP_GENERAL_EncryptionCertificateBase64 | `@Microsoft.KeyVault(SecretUri=https://<vault>.vault.azure.net/secrets/mcp-oauth-encryption/<version>)` |
| ASPNETCORE_ENVIRONMENT | Production |

General.json と環境変数の SigningCertificatePath／EncryptionCertificatePath は空にします。各用途で Path と Base64 を両方設定すると起動を拒否します。Base64 の実値を General.json や公開するファイルに書かないでください。

Key Vault の「証明書」から取得する PFX のパスワードは空です。CertificatePassword は空にし、以前の MCP_GENERAL_CertificatePassword が残っている場合は削除します。パスワード付き PFX を独自に Base64 化して「シークレット」に保存した場合だけ、そのパスワードを MCP_GENERAL_CertificatePassword の Key Vault 参照などで渡します。証明書をインポートするときのパスワードとは区別してください。

設定を保存し、ポータルで Key Vault 参照が解決されていることを確認してから再起動します。権限やネットワーク経路が不足して参照文字列がそのまま届く場合、証明書エラーで起動を止めます。解決後は /health/live、discovery、OAuth 認可から MCP 接続までを確認してください。

#### 4. 証明書を更新する

証明書は起動時に読み込むため、更新の適用には再起動が必要です。上の例はバージョンを固定し、新しい証明書が意図せず適用されることを防ぎます。暗号化用証明書を変えると、旧証明書で保護した Data Protection の鍵と既存の状態を復号できなくなります。複数インスタンスでは同じバージョンを揃えてください。

鍵を変更する更新では、停止して状態領域と旧バージョンを保全し、参照を新しいバージョンへ変更したうえで、専用の OAuth 状態と Data Protection の鍵を作り直し、利用者に再接続してもらいます。SQLite では StateDirectory、Redis ではラッパー専用の名前空間が対象です。旧鍵を使った状態を保持したまま自動で切り替える機能はありません。

## 8. Windows IIS

IIS への配置手順です。IIS 上での実機確認は未実施です。[Microsoft の IIS ホスティング資料](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/iis/?view=aspnetcore-10.0)も参照してください。

1. IIS を有効にした後、.NET 10 の **Hosting Bundle** をインストールし、IIS を再起動します。ASP.NET Core Runtime 単体では IIS 用モジュールが入りません。
2. 配布物を `C:\Apps\McpOAuthWrapper` などに展開します。生成済みの web.config を保持します。
3. 専用のアプリケーションプールを作り、.NET CLR は「マネージドコードなし」、32ビットアプリケーションは無効、ワーカープロセス数は1に設定します。SQLite 状態の同時使用を避けるため、重複リサイクルを無効にします。
4. 専用サイトとして HTTPS バインドと公開用証明書を設定し、配置先とアプリケーションプールを割り当てます。匿名認証を有効にします。Issuer はこのサイトのルート HTTPS URL です。
5. General.json／Rds.json を用意します。StateDirectory は `C:\ProgramData\McpOAuthWrapper\State` など配置先外にし、OAuth 用 PFX も別の保護されたフォルダーへ置きます。公開 HTTPS 用証明書とは用途が異なります。
6. `IIS AppPool\<プール名>` にアプリと証明書の読み取り、状態領域の変更権限を付けます。接続文字列と証明書パスワードは、保護したパラメータファイルまたはアプリプロセスの環境変数で設定します。環境は Production とします。
7. サイトを起動し、公開 URL の health、discovery、OAuth と MCP を確認します。IIS 統合の既定の転送設定を使用する場合、TrustedProxyAddresses の追加設定は不要です。

更新時はサイトを停止するか app_offline.htm を置いて停止を確認し、状態領域・設定・証明書を保持して配布物を更新します。更新完了後に app_offline.htm を削除して再起動します。

## 9. データベース別の設定

Dbms は `SQLServer`／`PostgreSQL`／`MySQL` のいずれかです。接続先の実際のスキーマと Users の読み取り権限を合わせてください。

| データベース | UserConnectionString の例（秘密は例示値） |
| --- | --- |
| SQL Server | `Server=sql.example;Database=Implem.Pleasanter;User ID=mcp_reader;Password=CHANGE_ME;Encrypt=True` |
| PostgreSQL | `Host=pg.example;Database=Implem.Pleasanter;Username=mcp_reader;Password=CHANGE_ME;Search Path='"Implem.Pleasanter"'` |
| MySQL | `Server=mysql.example;Database=Implem.Pleasanter;User ID=mcp_reader;Password=CHANGE_ME` |

PostgreSQL の大文字やピリオドを含むスキーマ名は二重引用符付きで指定します。JSON では内部の二重引用符を `\"` として記述します。SQL Server は接続ユーザーの既定スキーマに Users が見えることを確認します。読み取り対象は TenantId、UserId、LoginId、ApiKey、Disabled、Lockout、LoginExpirationLimit、LoginExpirationPeriod、LastLoginTime の9列です。

## 10. Redis／Valkey 互換 KVS モード

既定は SQLite です。OAuth の状態を KVS へ保存する場合は、General.json に次の設定を指定します。Pleasanter の Users を読む Rds.json は引き続き必要です。

```json
{
  "StateStore": "Redis",
  "KvsKeyPrefix": "pleasanter-mcp-oauth"
}
```

接続文字列は配置環境の `MCP_GENERAL_KvsConnectionString` に設定します。例えば TLS 接続なら `kvs.example:6380,ssl=true,user=wrapper,password=<接続用パスワード>` の形式です。実際の接続先が指定するポート・認証・TLS 設定を使用してください。KVS の資格情報を公開する設定例や配布 ZIP に含めないでください。

KVS に保存するのは OAuth クライアント、認可・トークンの状態、同意の識別子、ログイン試行回数、Data Protection の鍵です。**API キーそのものは KVS にも保存しません。** 認可とトークンには、キー再発行を検出する SHA-256 指紋が含まれます。

Redis モードではローカルの oauth.db／Data Protection 鍵ファイルを作りません。証明書を自動生成する用途だけは StateDirectory/certificates を使います。複数台ではこの証明書ディレクトリーを共有するか、同じ証明書をファイル、Base64、Windows ストア、クラウド方式で供給します。台ごとに別々の証明書を生成すると状態を共有できません。Data Protection の鍵は KVS に保存し、暗号化用証明書で保護します。

複数インスタンスでは、Issuer、テナント、クライアントなどの設定、KvsKeyPrefix、署名・暗号化証明書を揃えます。異なるラッパーの配置は別の KvsKeyPrefix を使います。キーは `{KvsKeyPrefix}:…` の形式で、Lua の原子的な更新に使うキーを同じ Redis Cluster スロットへ配置します。Cluster 構成自体の実機確認は未実施です。

KVS は OAuth の状態の保存先なので、意図せずキーが追い出されない noeviction の設定と、必要な可用性・永続化を用意してください。KVS の状態や鍵を失った場合は再接続が必要です。接続障害時に SQLite へ切り替える機能はありません。SQLite／Redis の状態を相互に移行しないため、モード切り替え時も利用者は再接続します。

認可コードと同意の二重使用、状態の同時更新、失効済みトークンの復活は KVS 内で原子的に拒否します。ログイン試行は15分、同意は5分の TTL を使用します。失効・期限切れの OAuth 状態は5分ごとに整理します。クライアント ID・トークンの参照 ID の検索には索引を使用し、一覧や認可の検索・整理は保存済みのエンティティを読み出して処理します。

Redis 8.2 と Valkey 9.1.2 の Docker 実機で、OAuth 認可・トークン更新・失効・MCP 中継、API キー非保存、再起動後の利用と別インスタンス間の競合を確認しています。Azure App Service／IIS では、配置後に認可から MCP 接続までを確認してください。

Claude・ChatGPT へ登録する操作は [AI アプリ接続手順](AIアプリ接続手順.md) を参照してください。

SQL Server の接続はラッパーが Encrypt=True（Mandatory）を必須にします。Encrypt=Strict は維持します。接続先には信頼できるサーバー証明書を用意してください。TrustServerCertificate=True は隔離した開発環境の自己署名証明書向けです。
